# Expense and reference-data API

The backend now persists expenses, allocations, and expense-origin debts through Prisma 7.10.1. The approved frontend remains a separate prototype and has not been connected to these endpoints. Independent loans, repayment mutations, balances across expenses, and financial revision/audit workflows are outside this stage.

All examples below are synthetic. Do not run them against a live database just to validate the code. Before any manual write, verify the branch in the Neon console and confirm that the locally configured connection belongs to the intended **development** branch. A database name or endpoint URL alone is not reliable evidence of branch identity. This implementation was validated with mocks, without verifying or writing to a configured Neon branch.

## Access and endpoints

Every route below inherits the global shared-session guard. State-changing requests also require the existing allowed `Origin`, session cookie, and `X-CSRF-Token`. Send JSON for POST/PATCH; DELETE can omit its body. Do not log headers or bodies containing cookies/tokens. Bootstrap/login instructions are in [authentication.md](authentication.md).

| Method and path | Behavior | Success |
| --- | --- | --- |
| `POST /api/expenses` | Create atomically, or replay the same client-generated ID | 201 |
| `GET /api/expenses` | Paginated active expenses, with optional financial filters | 200 |
| `GET /api/expenses/:id` | Details and retained history, including a deleted expense | 200 |
| `PATCH /api/expenses/:id` | Amend supplied fields and synchronize allocations/debts | 200 |
| `DELETE /api/expenses/:id` | Soft-delete the expense; repeated deletion is a no-op | 204 |
| `POST /api/expenses/:id/restore` | Validate and restore the parent; repeated restoration is a no-op | 200 |
| `POST /api/people`, `GET /api/people` | Create financial people and list active choices | 201 / 200 |
| `POST /api/categories`, `GET /api/categories` | Create categories and list active choices | 201 / 200 |
| `POST /api/payment-methods`, `GET /api/payment-methods` | Create typed methods and list active choices | 201 / 200 |

There are no individual authentication users. A person can be a beneficiary, funder, or external counterparty. The session authorizes access to the shared application; it never selects those financial roles. POV is neither an accepted request property nor an authorization/filter source.

## Creating an expense and safe retries

The caller must generate one UUID v4 **once per intended expense** (for example with `crypto.randomUUID()` in future frontend integration), retain it for retries, and submit it as `id`. Deliberately creating another expense requires a new UUID. This uses the existing expense primary key without a schema change.

```json
{
  "id": "00000000-0000-4000-8000-000000000030",
  "amount": "100.00",
  "purchasedOn": "2026-10-30",
  "merchant": "Example restaurant",
  "description": "Synthetic shared dinner",
  "categoryId": "00000000-0000-4000-8000-000000000010",
  "paymentMethodId": "00000000-0000-4000-8000-000000000020",
  "fundedByPersonId": "00000000-0000-4000-8000-000000000002",
  "classification": "SHARED",
  "allocations": [
    { "personId": "00000000-0000-4000-8000-000000000001", "percentage": "50" },
    { "personId": "00000000-0000-4000-8000-000000000002", "percentage": "50" }
  ]
}
```

An identical normalized payload with the same ID returns the existing resource, including its current history, without inserting allocations or debts. Equivalent decimal representations and participant order do not change this comparison. A different payload or a deleted expense with that ID returns 409. After an expense has been edited, an old creation payload can therefore conflict; do not generate a new ID automatically to bypass that conflict. Fetch the existing resource and resolve the intended action. This is resource-based idempotency, not a stored immutable request/response log.

The response includes the expense fields, `category`, `paymentMethod`, `fundedBy`, audit/deletion timestamps, and allocation/debt details. The following excerpt shows the non-funder's share from the synthetic example; IDs for allocations/debts are generated by Prisma:

```json
{
  "amount": "100.00",
  "currency": "PEN",
  "purchasedOn": "2026-10-30",
  "allocations": [
    {
      "personId": "00000000-0000-4000-8000-000000000001",
      "percentage": "50.0000",
      "amount": "50.00",
      "active": true,
      "deletedAt": null,
      "debt": {
        "origin": "EXPENSE",
        "debtorPersonId": "00000000-0000-4000-8000-000000000001",
        "creditorPersonId": "00000000-0000-4000-8000-000000000002",
        "currency": "PEN",
        "incurredOn": "2026-10-30",
        "originalAmount": "50.00",
        "repaidAmount": "0.00",
        "outstandingAmount": "50.00",
        "status": "OPEN",
        "deletedAt": null,
        "repayments": []
      }
    }
  ]
}
```

The complete response also contains the funder's S/ 50 allocation, with `debt: null`. This excerpt must not be interpreted as a one-person shared allocation.

## Input validation and reference data

- Money is a positive decimal **string**, at most 12 integral and two fractional digits, up to `999999999999.99`. Send a dot separator; JSON numbers, exponent notation, commas, zero, negative values, and excess scale are rejected. Currency is fixed to PEN and is not an input field.
- Allocation percentages are strings with at most four fractional digits, greater than zero and at most 100, totaling exactly 100. Send 1–20 unique beneficiaries. PERSONAL requires exactly one beneficiary; SHARED requires at least two. Clients cannot submit allocation amounts or debts; the server derives them.
- Dates must be real Gregorian calendar dates in `YYYY-MM-DD`, years 0001–9999. They become UTC-midnight Prisma Date values and are returned as date-only strings. Debt incurrence is always the purchase date, even for credit cards.
- All IDs are UUID v4, normalized to lowercase. Funder and beneficiaries are explicit. All referenced records must exist and be active for creation/amendment. Reading history and restoring a parent permit existing inactive reference records, since deactivation must not erase historical financial contributions.
- Merchant is trimmed, Unicode-normalized, nonblank, and at most 200 characters. Description is optional, at most 2000 characters; null/blank clears it. PATCH preserves omitted fields, accepts null only for description, and rejects an empty amendment. IDs, currency, deletion timestamps, balances, and POV are not editable fields.
- Delete and restore accept no financial fields; restore sends `{}`. Unexpected properties, including nested properties and unknown query parameters, are rejected by whitelist validation.

Reference creation bodies:

```json
{ "name": "Example relative", "notes": "Synthetic optional note" }
```

```json
{ "name": "Example groceries", "description": "Synthetic optional description" }
```

```json
{
  "name": "Example debit card",
  "type": "DEBIT_CARD",
  "ownerPersonId": "00000000-0000-4000-8000-000000000002",
  "description": "Synthetic optional description"
}
```

Reference names are trimmed/Unicode-normalized, nonblank, at most 120 characters, and compared case-insensitively for duplicates, including inactive records. People/categories/methods each have their own name namespace; method names must be unambiguous across owners/types. Optional notes/descriptions are at most 2000 characters. Allowed method types are CASH, BANK_TRANSFER, CREDIT_CARD, DEBIT_CARD, and OTHER. Owner is optional metadata and, when provided, must identify an active person. It never supplies an expense funder implicitly. No card numbers, CVV, PIN, credentials, or user-account properties are accepted. Deactivation/edit/delete endpoints for reference data are not implemented.

Reference creation returns the created model's ID, submitted metadata, `isActive`, and timestamps. Reference listing returns `{ data, total, page, pageSize }`, ordered by name then ID and restricted to active rows.

## Listing and filtering

All listing endpoints accept `page` (default 1, range 1–100000) and `pageSize` (default 20, range 1–100). Expense lists additionally accept:

| Parameter | Meaning |
| --- | --- |
| `purchasedFrom`, `purchasedTo` | Inclusive purchase-date range; start must not exceed end |
| `categoryId` | Explicit category UUID |
| `beneficiaryPersonId` | Person with an active allocation in the expense |
| `fundedByPersonId` | Explicit payer/funder UUID |
| `classification` | PERSONAL or SHARED |

Filters combine with AND. Expenses are ordered by purchase date descending, then ID descending. Archived allocations do not match the beneficiary filter. Example: `GET /api/expenses?page=1&pageSize=20&purchasedFrom=2026-10-01&purchasedTo=2026-10-31&classification=SHARED`.

Expense lists also return `{ data, total, page, pageSize }`; data contains the same representation as details. Count and page are read within one serializable snapshot. Separate page requests can still shift when records are inserted or edited between them; this is offset pagination, not a long-lived snapshot/cursor. Detail responses intentionally include archived allocations and repayment history, each with effective activity information. Consumers must use active allocations/debt status for totals rather than adding every historical row.

## Financial behavior

| Synthetic case | Allocations | Debt |
| --- | --- | --- |
| Antonella funds her own S/ 80 purchase | Antonella S/ 80 | None |
| Marco funds Antonella's S/ 150 purchase by card | Antonella S/ 150 | Antonella owes Marco S/ 150 from purchase date |
| Marco funds a S/ 100 shared dinner | Each S/ 50 | Antonella owes Marco S/ 50 |
| Marco funds S/ 100 split Antonella 70 / Marco 30 | Antonella S/ 70, Marco S/ 30 | Antonella owes Marco S/ 70 |
| An explicit third party funds both beneficiaries | Declared shares | Each non-funder owes their share to that funder |

All financial calculations use Prisma Decimal and the existing helpers. Largest-remainder apportionment works in integer cents, assigns extra cents by remainder, and resolves ties by stable person ID independently of request order, names, or POV. The final shares sum exactly to the expense. A tiny positive percentage may round to zero cents; it has an allocation but no zero-principal debt. No self-debts or automatic netting occur.

One expense/person allocation and one debt/source link remain reserved by the existing database unique constraints, including after deletion. Amendments reuse those records through upsert. Removed beneficiaries are soft-deleted; unpaid obsolete debts can become inactive or be reused for corrected terms. This preserves IDs/history links but is not a complete immutable revision log. No code physically deletes financial records or changes repayment rows.

Existing repayment history, including soft-deleted repayments, freezes that debt's principal, counterparties, and incurrence date. The service first rejects removal/overpayment conflicts and also rejects other changes to these frozen terms with 409. Metadata and other shares may change only if historically repaid obligations retain their terms. Even an increase in an already repaid debt requires a future explicit correction workflow. This conservative policy follows the existing database-design contract instead of silently rewriting settled obligations. Repayment CRUD is not part of this task.

## Transactions and concurrency

Creation, amendment, soft deletion, and restoration execute entirely in Prisma interactive **Serializable** transactions. Reference creation and consistent page/count reads also use the shared transaction helper. Database-dependent validation and complete financial-state reads happen inside the transaction. There are no network calls inside it. Prisma max-wait is five seconds and transaction timeout ten seconds.

Prisma `P2034` serialization/deadlock conflicts retry the **whole operation**, at most three attempts with 20/40 ms delays. A retry reloads current repayments and references rather than using a stale pre-transaction balance. Creation additionally retries unique-key races to recheck the requested ID. Exhaustion returns 409; the caller must preserve the original creation ID. Allocation synchronization follows stable person-ID order, and database unique constraints prevent duplicate source debts. No in-process mutex or session-scoped PostgreSQL lock is used, so consistency is not limited to one Node process.

Concurrent edits of the same expense serialize; after retry, a later successful absolute-field amendment wins for fields it explicitly supplied. This API has no optimistic version/If-Match contract. Other future financial writers, especially repayment creation/restoration, must follow the same serializable read/validate/write discipline. Direct SQL or noncompliant writers can bypass application invariants. People/payment-method name uniqueness is enforced by this API's serializable duplicate check; only categories currently have an additional SQL normalized-name index. No new indexes or schema changes were required.

The strategy follows [Prisma 7 transaction guidance](https://www.prisma.io/docs/orm/v7/prisma-client/queries/transactions). Mock tests verify the wrapper's isolation options, bounded retries, fresh repayment checks, and rollback expectations; they cannot prove PostgreSQL SSI behavior, adapter error mapping under real contention, cross-process interleavings, or live unique-index behavior. Those require a disposable integration database, separate from the live Neon development/production databases.

## Soft deletion and restoration

Deleting an expense changes only its `deletedAt`. Child allocation/debt/repayment flags and values remain untouched. Its debts and repayments immediately become effectively inactive through the parent, with zero active repaid/outstanding contribution. Original principal and all repayment rows remain visible in details. Active expense lists omit the parent.

Restoration validates allocation percentages/totals, active debt source/parties/principal/date consistency, current active repayment totals, and reference existence in the same transaction before clearing the parent flag. An inconsistent/overpaid obligation prevents restoration. Independently deleted allocations, debts, and repayments remain deleted. If independently removed allocations no longer total 100%, the parent cannot be restored until an explicit correction resolves that inconsistency; the endpoint does not silently recreate children.

## Errors

| Status | Examples |
| --- | --- |
| 400 | DTO/decimal/date/percentage errors, missing or inactive selected references, invalid range, empty amendment |
| 401 | Missing/expired shared session |
| 403 | Missing/forged CSRF, disallowed Origin, non-JSON mutation |
| 404 | Unknown expense UUID |
| 409 | Reused creation ID with different fields, duplicate name, repayment conflict, inconsistent restoration, unresolved transaction conflict |
| 500 / 503 | Generic internal failure / recognized temporary database unavailability |

Controller exception filters preserve intentional HTTP errors and replace database/internal exceptions with safe messages. They never return driver details, connection strings, raw SQL, or stack traces. Successful private responses inherit `Cache-Control: no-store`. Do not add request-body/query/cookie logging for troubleshooting financial data.

## Validation and limits

Run backend `npm run prisma:validate`, `npm run prisma:generate` (also part of prebuild), `npm run lint`, `npm test`, `npm run test:e2e`, and `npm run build`. Test fixtures use only synthetic IDs/values and mock Prisma; no migration, reset, seed, live server startup, or database write is needed. The current CI workflow discovers the new test files automatically.

Validation passed: lint without warnings, production build, **95 unit tests** and **70 API tests** including the existing suites. New tests cover personal/shared/third-party funding, exact cents, invalid/duplicate participants and references, safe creation replay, debt-link reuse, amendments, frozen repayment terms, soft deletion/restoration, pagination/filters, every route's authentication, mutation CSRF, whitelist rules, rollback expectations, and transaction conflicts.

No schema/migration files or dependency versions changed. No real database records were created during validation, and no live Neon branch identity/connectivity was asserted. Actual concurrent PostgreSQL integration testing and an immutable correction/audit workflow remain outstanding. Production session/cookie deployment limitations remain those documented in authentication.md. Measure query behavior against representative isolated data before adding indexes or changing pagination; this initial implementation bounds expense pages but includes related history.
